# Замовлення, атрибуція, воронка замірів і ручні бюджети

Роботу розбито на 5 блоків, які виконуються по черзі. Кожен блок завершується перевіркою, публікації без вашого дозволу не буде.

## 1. Плашка «Активні замовлення за період» на дашборді
- Поруч із «Сумою договорів» з'являється друга плашка: сума всіх активних замовлень за вибраний період (крім відмов). Для вересня це близько 3,74 млн ₴ проти 126 620 ₴ договорів.
- Під плашкою дві розбивки: по каналах (Google Ads, Meta, OLX, сарафан, сайт тощо) і по менеджерах. Сума, кількість і частка кожного.
- Дата замовлення — реальна дата створення в KeyCRM, а якщо її немає — дата внесення в систему.
- Клік по каналу або менеджеру відкриває список його замовлень.

## 2. Статуси KeyCRM → статуси договору, реальний ROMI
- Налаштовувана таблиця відповідностей у Налаштуваннях: статус KeyCRM → комерційний статус ERP (наприклад «Виконано/Оплачено» → «Продано», «В роботі» → «Договір», «Скасовано» → «Відмова»). Ви зможете її змінювати без програміста.
- Нова синхронізація одразу ставить правильний статус. Для 183 наявних замовлень KeyCRM — одноразове оновлення статусу за цією таблицею (ручні статуси, змінені людьми, не чіпаються).
- Нерозпізнані назви джерел KeyCRM («Facebook Leads», «Сарафан…», «Сайт terzi.biz (форма)», «OLX») отримують відповідність каналам.
- Якщо в замовленні немає UTM/каналу — він береться з пов'язаного ліда.
- Маркетингова аналітика: під кожним каналом/кампанією розкривається список замовлень (дата, сума, валовий прибуток, ROMI) з переходом у картку замовлення. Оплати беруться з Finmap.

## 3. Лід = замовлення, одна картка
- Коли лід переходить у фінальну успішну стадію («Договір заключено / успішно реалізовано»), автоматично створюється замовлення (або прив'язується наявне), з перенесенням клієнта, телефону, джерела, UTM, менеджера, замірів і кошторисів. Повторного замовлення не буде.
- Картка замовлення і картка ліда стають однією карткою: той самий вигляд і ті самі вкладки (клієнт, дзвінки, заміри, кошториси, фінанси, файли, історія). У замовленні додатково — виробництво і оплати.
- З ліда й з замовлення можна перейти одне в одне; зміни клієнта/телефону видно в обох.

## 4. Воронка замірів як у лідів
- Сторінка «Заміри» отримує канбан-дошку, як у лідів: колонки «Заплановано → Підтверджено → Виїхали → Виконано → Кошторис → Скасовано/Перенесено», перетягування між колонками.
- Колонки налаштовуються в Налаштуваннях (назви, порядок, кольори).
- Клік відкриває ту саму картку заміру, яка відкривається з ліда. Створення заміру з календаря, ліда чи дошки — всюди один запис.

## 5. Ручні бюджети і випадні списки
- Сторінка «Бюджети» в Маркетингу: ручне внесення витрат для каналів без інтеграції (зовнішня реклама, OLX, листівки, виставки тощо) — канал, кампанія (необов'язково), період або дата, сума в ₴, примітка. Ці витрати входять у CPL/ROMI так само, як Google/Meta.
- Випадні списки замість вільного тексту: джерело ліда, канал, кампанія, менеджер, послуга/напрямок, причина відмови, тип заміру, статуси. Значення керуються у Налаштуваннях → «Довідники», можна додавати свої варіанти.

## Технічні деталі
- Дашборд: `orders_value` + розбивки вже є в `analytics_overview`; додати поле в `HeroStrip`/`index.tsx` і drawer зі списком.
- Статуси: нова таблиця `keycrm_status_map` (status_id/group → commercial_status), читається в `applyOrderCard`; бекфіл через data-запит лише для `external_source='keycrm'` без ручних змін; джерела — доповнення `marketing_source_map`/`normalize_marketing_source`.
- UTM-успадкування: у `linkLeadToOrder` заповнювати лише порожні `utm`/channel/campaign.
- Лід→замовлення: серверна дія на зміну стадії з прапорцем `is_won` у `crm_stages`; ідемпотентно через `crm_leads.order_id`; спільний компонент картки для `LeadCardDialog` і `orders.$id`.
- Воронка замірів: нова таблиця `measurement_stages` + колонка `stage_id` у `order_measurements` (адитивно, бекфіл зі статусу).
- Бюджети: існуюча `marketing_manual_spend` підключається до `getMarketingEconomics`; UI у `/marketing/budgets`.
- Довідники: переважно існуючі таблиці (`marketing_channels`, `close_reasons`, `crm_stages`), плюс універсальна `config_entries` для решти.
- Після кожного блоку: typecheck, тести, перевірка в прев'ю на мобільному.
