# SCHEMA_DRIFT.md — узгодження міграцій і фактичної схеми

Мета: жодних несподіванок при `db:reset` на чистій базі. Тут фіксуються всі
відомі розбіжності між `supabase/migrations/` і production-схемою.

## Як перевіряти

```bash
npm run db:validate    # структура міграцій: GRANT, RLS, політики, іменування
npm run db:snapshot    # знімок схеми (таблиці, колонки, політики, тригери)
npm run db:reset       # чиста база з нуля: міграції + seed
```

Після кожної зміни схеми оновлювати цей файл.

## Категорії розбіжностей

| Категорія | Опис | Дія |
| --- | --- | --- |
| A. Об'єкт існує в БД, немає в міграціях | створено поза історією | додати reconciliation-міграцію `IF NOT EXISTS` |
| B. Об'єкт є в міграціях, немає в БД | міграція не застосована | застосувати, зафіксувати |
| C. Розбіжність у політиках/грантах | різні умови RLS | вирівняти новою міграцією |
| D. Історичні міграції без GRANT | ранній період проєкту | додаткова міграція з GRANT |

## Відомі позиції

| # | Категорія | Об'єкт | Стан | Примітка |
| --- | --- | --- | --- | --- |
| 1 | D | ранні таблиці `catalog_items`, `coefficients`, `formulas` | до перевірки | створювались до правила «GRANT у тій самій міграції»; перевірити наявність грантів для `authenticated`/`service_role` |
| 2 | C | `integration_oauth_states`, `integration_tokens` | свідомо | RLS увімкнено, політик немає — доступ тільки через service_role (fail-closed) |
| 3 | A | `docs/migrations/pending/2026-08-25_pvc_d15_split.sql` | не застосовано | розділення Sikaplan D-15 на окремі коди каталогу |

## Правила reconciliation-міграцій

- Тільки additive: `CREATE ... IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`,
  `DROP POLICY IF EXISTS` + `CREATE POLICY`.
- Не змінювати наявні дані без окремого затвердження.
- Кожна reconciliation-міграція описується рядком у таблиці вище зі статусом.
