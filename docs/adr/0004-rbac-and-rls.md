# ADR 0004 — модель прав: RBAC + RLS

Статус: прийнято

## Контекст

У системі співіснують enum `app_role` (на нього спираються RLS-політики) і
таблиці гранульованих прав `access_roles` / `role_permissions` / `user_access`
(модуль «Доступи»). Без синхронізації вони давали розбіжні результати.

## Рішення

- Джерело правди для бізнес-ролі користувача — `user_access.role_key` у зв'язці
  з `access_roles` і `role_permissions`.
- `public.user_roles` (enum `app_role`) — **похідна** проєкція, яку підтримує
  тригер `sync_user_roles_from_access()`; вона обслуговує RLS-політики й
  `public.has_role()`.
- Ролі ніколи не зберігаються в `profiles` чи будь-якій таблиці користувача.
- RLS увімкнено на всіх таблицях `public`; кожна нова таблиця отримує
  GRANT → ENABLE RLS → POLICY в одній міграції.
- Перевірка ролі в SQL — через SECURITY DEFINER функції з фіксованим
  `search_path` (`public.has_role`, `private.*`), щоб уникнути рекурсії політик.
- `supabaseAdmin` (service_role) використовується лише після явної перевірки
  прав у серверній функції; ніколи для звичайних читань.

## Наслідки

- Зміна ролі в модулі «Доступи» автоматично відображається на RLS.
- Internal-фінанси (собівартість, маржа, прибуток, ФОП, комісії) закриті і
  політиками, і перевірками на сервері, і фільтрацією DTO.
