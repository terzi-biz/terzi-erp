# FRONTEND_AUDIT — аудит фронтенду

Обмеження середовища: `LOVABLE_BROWSER_AUTH_STATUS=signed_out`. Активної сесії немає, автентифіковані сторінки в браузері не перевірялися. Весь аудит нижче — статичний аналіз коду (grep, читання файлів, `tsgo --noEmit`). Де рантайм-поведінку неможливо підтвердити — позначено «НЕ ПЕРЕВІРЕНО».

### 1. [CRITICAL] Помилки типів TS2741: три `<Link>` без обов'язкового `search`-параметра
**Доказ:**
- `src/components/AppShell.tsx:157` — `<Link to={`/${m}`}>` (шаблон `/screed`, `/roofing`, `/insulation`, `/demolition`) без `search`.
- `src/routes/clients.tsx:178` — `<Link to="/screed">` без `search`.
- `src/routes/index.tsx:59` — `<Link to="/screed">` без `search`.
- Підтверджено компілятором: `npx tsgo --noEmit` видає 3× `error TS2741: Property 'search' is missing... required in type ... "/screed"`.
- Причина: маршрути `/materials`, `/works`, `/equipment`, `/logistics` мають `validateSearch` з обов'язковим `module` (materials.tsx:18, works.tsx:18, equipment.tsx:10, logistics.tsx:10), і router вимагає обов'язковий search для будь-якого посилання на ці й пов'язані типізовані маршрути; конкретно тут страждають посилання саме на калькулятори (`/screed` та шаблон `/${m}`).

**Вплив на бізнес:** Це помилки типізації, що блокують «чистий» build/typecheck CI і сигналізують про реальний навігаційний дефект: кнопки «Новий кошторис» на дашборді (`index.tsx:59`), «+ Новий» у картці клієнта (`clients.tsx:178`) та пункт «Калькулятор» у розкривному меню модуля (`AppShell.tsx:157`) не передають параметр модуля/типу розрахунку туди, де інші аналогічні посилання (напр. `AppShell.tsx` — «Матеріали», «Роботи», «Обладнання», «Логістика» для того ж модуля) явно передають `search={{ module: m }}`. Якщо `/screed` очікує який-небудь обов'язковий контекст (наприклад, вибраний модуль чи id кошторису) — користувач після кліку може потрапити на калькулятор без потрібного стану/дефолтів, що на практиці виглядає як «кнопка веде в порожню/неправильну форму».

**Рекомендація:** Привести три виклики `<Link>` у відповідність до типізованого контракту маршруту — додати відповідний `search` (наприклад, `search={{ module: m }}` в AppShell.tsx:157, і за потреби дефолтний `search={{}}`/конкретне значення в clients.tsx:178 та index.tsx:59), або, якщо це навмисно «створити новий без прив'язки до модуля», зробити `search`-схему `/screed` з опціональними полями (partial) замість обов'язкових, узгодивши з очікуваннями сторінки `/screed`.

### 2. [HIGH] Відсутність єдиного, свідомого підходу до захисту сторінок (`beforeLoad`) — 19 з 34 файлів без явного route-level guard
**Доказ:** `grep -L "beforeLoad" src/routes/*.tsx` повертає 19 файлів, серед яких `branding.tsx`, `directions-editor.tsx`, `equipment.tsx`, `history.tsx`, `index.tsx`, `insulation.tsx`, `integrations.tsx`, `login.tsx`, `logistics.tsx`, `materials.tsx`, `operations.tsx`, `production.$id.tsx`, `production.index.tsx`, `reports.tsx`, `roofing.tsx`, `screed.tsx`, `settings.tsx`, `works.tsx`, `demolition.tsx`. Частина з них (index.tsx:26, operations.tsx:72, reports.tsx:16, settings.tsx:118, history.tsx:66, production.index.tsx:26, production.$id.tsx:34, screed.tsx:88, roofing.tsx:79, insulation.tsx:51, demolition.tsx:42, integrations.tsx:62) читає `useAuth()` всередині компонента — це відбувається вже після монтування компонента й початку рендеру/запитів даних, а не до нього, на відміну від маршрутів із `beforeLoad`+`redirect` (напр. `access.tsx:22`, `clients.tsx:13`, всі `crm.*.tsx`). Для `branding.tsx`, `directions-editor.tsx`, `equipment.tsx`, `logistics.tsx`, `materials.tsx`, `works.tsx` не знайдено взагалі жодної перевірки авторизації у файлі (ні `beforeLoad`, ні `useAuth`).

**Вплив на бізнес:** Непослідовний захист — частина сторінок (CRM-модуль, доступи, клієнти) блокує неавторизований доступ ще на етапі завантаження маршруту, а частина (адмінські «Інтеграції», «Конструктор напрямків», калькулятори, каталоги матеріалів/робіт/обладнання/логістики) покладається лише на клієнтський рендер або взагалі не має видимої перевірки в самому route-файлі. Це підвищує ризик короткочасного «блимання» захищеного контенту (flash of protected content) до редиректу, а для файлів без жодної перевірки — ризик показу даних/форм без авторизації, якщо серверні функції самі не гарантують RLS/перевірку ролей (це не перевірялося — поза межами аудиту фронтенду). Це прямий фінансовий/репутаційний ризик для B2B-системи з ролями (адмін/директор/фінансист/менеджер).

**Рекомендація:** Уніфікувати захист на рівні `beforeLoad` для всіх приватних маршрутів (за зразком `access.tsx`, `crm.*.tsx`), прибравши дублювання логіки `useAuth()`-перевірки в тілі компонентів; для `branding.tsx`, `directions-editor.tsx`, `equipment.tsx`, `logistics.tsx`, `materials.tsx`, `works.tsx` — додати явний `beforeLoad` з редиректом на `/login`, якщо ці сторінки не мають бути публічними.

### 3. [HIGH] Відсутність error boundary/станів помилки на рівні даних для більшості сторінок
**Доказ:** `grep -n "errorComponent" src/routes/*.tsx` дає лише один результат — `src/routes/__root.tsx:31` (глобальний `errorComponent`, що просто робить `console.error` — root.tsx:32, — без користувацького UI відновлення, судячи з сигнатури `({ error }: { error: Error }) => {`, тіло не деталізовано в межах виділеного бюджету часу, **частково НЕ ПЕРЕВІРЕНО**). Жоден з 34 route-файлів не визначає власний `errorComponent`. Водночас у частині сторінок (`crm.calls.tsx`, `crm.contacts.tsx`, `crm.requests.tsx`, `crm.tasks.tsx`, `access.tsx`, `directions-editor.tsx`) помилки мутацій обробляються лише через `toast.error` (напр. `crm.calls.tsx:66`, `access.tsx:132,138`) — це покриває помилки запису (mutation), але не показує явний стан помилки для основного запиту читання (`useQuery`) на переважній більшості сторінок: жоден з переглянутих файлів (`crm.index.tsx`, `crm.leads.tsx`, `history.tsx`, `reports.tsx`, `production.index.tsx`, `settings.tsx`) не деструктурує і не використовує поле `error`/`isError` з `useQuery`.

**Вплив на бізнес:** Якщо серверна функція (наприклад, `listEstimates`, `listObjects`, `listProductionEstimates`) впаде з помилкою (мережа, RLS, 5xx), користувач з великою ймовірністю побачить порожній список/дашборд без пояснення причини — це виглядає як «дані зникли» і провокує повторні звернення в підтримку та недовіру до системи фінансової/виробничої звітності.

**Рекомендація:** Додати per-route `errorComponent` для ключових сторінок (щонайменше `/history`, `/reports`, `/production/*`, `/objects/*`, `/crm/*`) або єдиний UI-компонент стану помилки, підключений через `isError`/`error` з `useQuery`, з можливістю retry.

### 4. [MEDIUM] Дублювання layout-логіки авторизації та порожніх станів між файлами калькуляторів
**Доказ:** `demolition.tsx:42`, `insulation.tsx:51`, `roofing.tsx:79`, `screed.tsx:88` — усі чотири незалежно повторюють `const { roles, profile } = useAuth();` та (за структурою файлів) власну форму збереження з `useMutation`/`toast.error` (напр. `demolition.tsx:95`, `demolition.tsx:127`). Розміри файлів близькі й істотні: `insulation.tsx` — 331 рядок, `roofing.tsx` — 448, `screed.tsx` — 475, `demolition.tsx` — 301 — сумарно 1555 рядків для чотирьох дуже схожих калькуляторів, без спільного базового компонента в `src/routes` (спільний код, якщо є, винесено поза `src/routes`, що не перевірялося детально в межах бюджету часу — **ЧАСТКОВО НЕ ПЕРЕВІРЕНО**, чи є спільний `src/components`/`src/lib` шар, що реально усуває дублювання логіки саме UI-станів).

**Вплив на бізнес:** Будь-яка зміна бізнес-правила (напр. нове поле кошторису, нова валідація) вимагає синхронних правок у 4 майже ідентичних файлах — це підвищує вартість підтримки і ризик розбіжностей (одну сторінку поправили, іншу забули).

**Рекомендація:** Винести спільний UI-шаблон калькулятора (форма позицій, підсумок, кнопка збереження, обробка помилок) у переговорений спільний компонент/хук у `src/components`, залишивши в `src/routes/*.tsx` лише конфігурацію, специфічну для модуля.

**Доказ:** Пошук латинських службових слів (`loading...`, `please`, `error occurred`, `Cancel`, `Save`, `Delete`) дав збіги у 16 файлах: `access.tsx`, `crm.calls.tsx`, `crm.contacts.tsx`, `crm.leads.tsx`, `crm.requests.tsx`, `crm.tasks.tsx`, `demolition.tsx`, `directions-editor.tsx`, `insulation.tsx`, `integrations.tsx`, `objects.$id.tsx`, `operations.tsx`, `production.$id.tsx`, `roofing.tsx`, `screed.tsx`, `settings.tsx`. **Вплив на бізнес:** НЕ ПЕРЕВІРЕНО остаточно, чи ці збіги — видимий користувачу текст чи технічні ідентифікатори (наприклад, `status: "answered"` в `crm.calls.tsx:28`, назви CSS-класів, `console.error`). Потенційний ризик — окремі кнопки/лейбли можуть залишитися англійською серед переважно українського інтерфейсу, що виглядає непрофесійно для клієнта.

**Рекомендація:** Провести цільовий по-файловий перегляд знайдених 16 збігів (окремою задачею — за межами 15-хвилинного бюджету цього аудиту) і замінити будь-який видимий користувачу англомовний текст на українські відповідники, консолідувавши через `src/lib/i18n` (вже використовується частково — `useT()`, `useI18n()` в `AppShell.tsx`).

### 9. [LOW] Доступність (accessibility) — не перевірено предметно, орієнтовний ризик
**Доказ:** У переглянутих фрагментах кнопки часто складаються лише з іконки (`lucide-react`) без видимого тексту й без `aria-label` (напр. `AppShell.tsx:117` — кнопка закриття drawer `<button onClick={...}><X className="w-5 h-5" /></button>` без `aria-label`; аналогічно кнопка `Trash2` в `clients.tsx:181-183`). Повний аудит доступності (контраст, фокус-стани, `aria-*`) не проводився — **НЕ ПЕРЕВІРЕНО** через обмеження бюджету часу і неможливість інтерактивної перевірки в браузері без сесії.

**Вплив на бізнес:** Іконки-кнопки без `aria-label` погіршують досвід користувачів скрінрідерів і ускладнюють автоматизоване QA/e2e-тестування, що спирається на доступні імена елементів.

**Рекомендація:** Провести окремий acceessibility-аудит (axe-core/Lighthouse) з автентифікованою сесією; в першу чергу додати `aria-label` до icon-only кнопок у `AppShell.tsx` та формах CRM/клієнтів.
