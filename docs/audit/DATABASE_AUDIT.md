# DATABASE_AUDIT.md — аудит бази даних

Метод: read-only SQL до системних каталогів і до даних, 01.08.2026. Дані не змінювались.
Кількісна інвентаризація — у DATABASE_MATRIX.md.

## 1. Загальний стан

64 таблиці, 138 індексів, 53 тригери, 29 enum, 33 міграції, 0 view, 0 функцій-агрегатів.
RLS увімкнено скрізь. Загальний обсяг даних мізерний (найбільша таблиця — `role_permissions`, 1656 рядків), тобто система **ще не в реальній експлуатації**: 51 кошторис, 7 клієнтів, 5 об'єктів, 3 ліда, 1 контакт, 1 задача.

Це важливо для трактування решти висновків: проблеми продуктивності поки не проявляються, але структурні дефекти вже зафіксовані в схемі й проявляться одразу після імпорту 3541 покупця і 1946 карток із keyCRM.

## 2. Критичні дефекти моделі даних

### 2.1 Кошториси не пов'язані з клієнтами і об'єктами (CRITICAL)

```
select count(*), count(client_id), count(object_id) from estimates;
-> 51, 0, 0
```

Усі 51 кошторис мають `client_id IS NULL` і `object_id IS NULL`. Замість FK використовуються текстові поля `client_name`, `client_phone`, `object_address`. Наслідки:
- у картці клієнта неможливо показати його кошториси через зв'язок — лише пошуком по рядку;
- перейменування або злиття клієнта розриває зв'язок;
- будь-яка аналітика «сума кошторисів по клієнту / по об'єкту» неможлива;
- ланцюг «Клієнт → Об'єкт → Замір → Розрахунок → Кошторис» із Project Knowledge **фактично розірваний** у центральній ланці.

### 2.2 Чотири паралельні сховища одного розрахунку (HIGH)

Таблиця `estimates` містить одночасно `payload`, `calculation_json`, `client_lines`, `internal_lines` (усі jsonb). Немає інваріанту, який з них є істиною. Різні місця коду читають різні поля, тому розбіжність між «внутрішнім» і «клієнтським» виглядом кошторису не детермінована схемою, а залежить від того, який код останнім записував.

Додатково: рядки кошторису зберігаються як JSON, а не окремою таблицею. Це унеможливлює SQL-звіти по матеріалах/роботах (наприклад «скільки праймера продано за квартал») без парсингу JSON у застосунку.

### 2.3 Немає soft delete (HIGH)

У жодній із 64 таблиць немає колонки `deleted_at` (перевірено по `information_schema.columns`). Таблиця `archived_records` створена, але порожня і **в коді не використовується** (0 посилань). Тобто вимога Project Knowledge «soft deletion» не виконана: `DELETE` політики на `clients`, `objects`, `estimates`, `crm_leads` видаляють дані фізично і незворотно.

### 2.4 Немає версіонування записів і захисту від конкурентного запису (HIGH)

Немає колонок `version`/`lock_version`, немає перевірки `updated_at` при UPDATE. Два менеджери, що одночасно редагують кошторис або картку клієнта, мовчки перезаписують зміни один одного. Для системи з узгодженням кошторисів це прямий шлях до втрати погоджених цін.

### 2.5 Історія цін не ведеться (HIGH)

`price_history` — 0 рядків, 0 посилань у коді. Вимога «ніколи не перезаписувати історичні ціни, створювати нову версію» **не реалізована**: `catalog_items` (192 рядки) редагується напряму з автозбереженням (дебаунс 1.5 с у `src/components/CatalogPage.tsx`). Кошторис, сформований минулого місяця, після зміни прайсу перерахується за новими цінами, бо `estimates` не зберігає версію прайс-листа (`price_book_version` як колонки немає).

### 2.6 Модуль файлів не існує (HIGH)

`object_files` має 4 RLS-політики і 0 рядків. У `storage.buckets` — **0 бакетів**. У `src/` немає жодного виклику `storage.from(...)` і жодного upload-компонента. Читання файлів реалізовано (`src/lib/objects.functions.ts:124`), запис — ні. Вкладки «Файли/Документи» в картці об'єкта не можуть працювати.

### 2.7 Порожні таблиці, від яких залежить RLS (MEDIUM)

`object_assignments` — 0 рядків, але вона входить у політику `objects_read_scoped` як єдиний спосіб дати доступ виконавцю, який не є owner/manager. Поки таблиця порожня, бригадир не бачить жодного об'єкта, крім своїх власних. Механізм призначень у UI фактично не заповнюється.

## 3. Мертві та неузгоджені об'єкти

Таблиці з нульовими посиланнями в коді: `additional_services`, `archived_records`, `client_groups`, `estimate_sections`, `formulas`, `price_history`, `access_permissions` (остання читається лише зсередини SQL-функції `has_permission`, тому не зовсім мертва).

`estimate_sections` + `formulas` + `directions` + `input_fields` — це «двигун напрямків» (`src/lib/engines/direction-engine.ts`, `formula-eval.ts`, сторінка `/directions-editor`). У БД він містить 3 напрямки, 4 секції, 2 формули, 48 полів, але реальні калькулятори (`screed`, `roofing`, `insulation`, `demolition`) рахують за захардкодженою логікою в `src/lib/*-calc.ts`, а не через цей двигун. Тобто **побудовано дві конкурентні системи розрахунку, і декларативна не використовується**.

## 4. Індекси та продуктивність схеми

**46 зовнішніх ключів без індексу.** Перелік (таблиця → колонка):

`calendar_events` → booking_id, client_id, created_by, estimate_id, manager_id, measurement_id, responsible_user_id;
`clients` → owner_id; `crew_bookings` → created_by;
`crm_calls` → contact_id, lead_id; `crm_leads` → client_id, contact_id, object_id, pipeline_id;
`crm_requests` → contact_id, lead_id; `crm_tasks` → client_id, contact_id, lead_id, object_id;
`estimate_audit_log` → actor_id; `estimate_versions` → approved_by; `estimates` → direction_id;
`integration_conflicts` / `integration_event_logs` / `integration_field_mappings` / `integration_oauth_states` / `integration_webhooks` → integration_id; `integrations` → provider_key;
`object_assignments` → object_id, user_id; `object_comments` → author_id, object_id, parent_id;
`object_files` → object_id, uploaded_by, zone_id; `object_measurements` → object_id, surveyor_id;
`object_status_history` → changed_by, object_id; `object_zones` → object_id;
`registration_approvals` → reviewed_by; `user_access` → role_key; `user_invitations` → role_key.

Особливо болісно це для `clients.owner_id` і `crm_*`: RLS-політики фільтрують саме по цих колонках, тобто **кожен запит користувача робить seq scan** з перевіркою прав по кожному рядку. На 7 клієнтах непомітно, на 3541 імпортованому покупці — помітно одразу.

Статистика підтверджує: `catalog_items` — 1111 seq scan, `estimates` — 686, `clients` — 138, `profiles` — 217.

Також відсутні очевидні складені індекси під типові вибірки: `estimates(owner_id, created_at desc)`, `crm_leads(stage_id, assigned_to)`, `calendar_events(starts_at, crew_id)`.

## 5. Цілісність і типи

- `numeric` для грошей використовується (добре), але **немає CHECK-обмежень** на невід'ємність сум, площ, кількостей. Порожні або від'ємні значення можуть потрапити в кошторис.
- Немає `CHECK` на узгодженість статусних переходів — статус міняється будь-яким UPDATE.
- 29 enum-типів: зміна значення enum потребує міграції; частина статусів дублюється текстовими полями в інших таблицях.
- Часові мітки: `timestamptz` — коректно; але прикладний часовий пояс Europe/Kyiv ніде в БД не зафіксований, форматування лише на клієнті.

## 6. Ризики міграції keyCRM

`integration_sync_links` вже містить 274 записи, `integration_event_logs` — 677. При цьому `integration_import_runs` порожня, тобто **повний початковий імпорт ще не запускався**. Заплановане завантаження 3541 buyers + 1946 lead cards + 116 orders потрапить у таблиці, які:
- не мають індексів на FK (п.4);
- не мають soft delete (п.2.3) — помилковий імпорт неможливо відкотити;
- пишуться в **ту саму базу, що й прод** (окремого середовища немає).

Це найвищий операційний ризик найближчого етапу.
