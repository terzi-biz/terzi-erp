# KNOWN_ISSUES.md

Реєстр відомих обмежень. Кожен пункт: проблема → вплив → пропозиція.

| # | Проблема | Вплив | Пропозиція |
| --- | --- | --- | --- |
| 1 | Preview і production можуть використовувати одну базу | тестові дії пишуть у бойові дані | окремий dev-проєкт БД, `.env` на середовище |
| 2 | Два шляхи доступу до даних (прямий PostgREST з браузера і серверні функції) | правила дублюються, ризик розбіжності | поступово переносити критичні читання/записи в серверні функції |
| 3 | Дві моделі ролей: enum `app_role` і `access_roles`/`role_permissions` | можлива розсинхронізація прав | лишити `access_roles` єдиним джерелом, `user_roles` — похідне через тригер (частково зроблено) |
| 4 | Немає soft delete (`deleted_at`) | видалення незворотні | додати `deleted_at` для ключових таблиць і фільтри в політиках |
| 5 | Немає оптимістичних блокувань | паралельне редагування перетирає зміни | версія рядка + перевірка при UPDATE |
| 6 | Storage-бакетів немає, файли замовлення не завантажуються | модуль файлів неповний | створити бакет + політики + UI завантаження |
| 7 | Частина ранніх міграцій без явних GRANT | ризик недоступності таблиці на чистій базі | reconciliation-міграція, див. `docs/SCHEMA_DRIFT.md` |
| 8 | Кошториси історично без `client_id`/`order_id` | розриви в аналітиці | добэк-філ через `/data-audit` з аудитом |
| 9 | Немає ретеншн-політики для `integration_events` / `audit_logs` | зростання обсягу | періодична архівація старих подій |
| 10 | Мобільна верстка складних таблиць залишається щільною | UX на телефоні | картковий режим для решти реєстрів |

Пункти не блокують експлуатацію; пріоритети — у `docs/ROADMAP.md`.
